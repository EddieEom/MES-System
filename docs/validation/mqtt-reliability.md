# MQTT 장애 복구·부하 시험

## 변경 목적과 범위

기존 Gateway는 Clean Session과 기본 구독 QoS를 사용했고, 연결 해제 후 로그만 남겼습니다. 이번 변경은 고정 Client ID, `CleanSession(false)`, QoS 1 구독과 단일 재연결 루프를 추가합니다. 최초 연결 실패도 1초 간격으로 재시도하며 종료 요청 시 재연결 루프를 취소하고 클라이언트를 정리합니다. `MES_MQTT_HOST`, `MES_MQTT_PORT`, `MES_MQTT_CLIENT_ID`로 환경을 지정합니다. 같은 Client ID를 여러 Gateway에서 공유하면 서로 연결을 끊을 수 있습니다.

시험은 실제 `MqttClientService.cs`를 링크해 실행합니다. PLC/COM 의존성을 제외하기 위해 운영 Router 대신 ID 수집 핸들러를 주입합니다. 운영 DB·HTTP·제품 상태 변경·WinForms는 이 시험에 포함되지 않습니다.

## 실행

.NET 8 SDK가 필요하며 별도 PLC·SQL Server·Mosquitto 설치는 필요하지 않습니다.

```bash
dotnet run --project tests/MqttReliability -c Release
```

- 기본: 10,000개, 목표 초당 1,000개. 실제 처리율은 결과 JSON의 observedMessagesPerSecond로 확인합니다.
- 수신측 TCP 경로를 차단하고, 브로커가 살아 있는 상태에서 QoS 1 메시지 100개를 추가 발행합니다.
- TCP 경로 복구 후 전체 ID 누락 여부, 중복 수, 연결 횟수, 종료 후 재연결 여부를 확인합니다.
- 결과: `TestResults/mqtt-reliability.json`.
- 연속 수신 시험 예: `MES_TEST_COUNT=600000 MES_TEST_RATE=1000 dotnet run --project tests/MqttReliability -c Release` (목표 10분; 실행 전후 조건과 실제 소요시간 확인 필요).

## 보장하지 않는 것

QoS 1은 적어도 한 번 전달하므로 중복이 가능합니다. 발행측도 QoS 1 이상을 사용해야 하며, 브로커의 세션 보관 한도·디스크 영속화 설정에 따라 결과가 달라집니다. 이 시험은 브로커 프로세스를 재시작하지 않습니다. 장비가 네트워크 단절 중 새 데이터를 발행할 수 없다면 발행측의 로컬 저장과 재전송도 필요합니다.

MQTT ACK는 DB 커밋 확인이 아닙니다. 운영 Router는 일부 예외를 내부에서 처리하며, API 실패 기록 파일도 자동 재처리 큐가 아닙니다. 현재 변경은 DB 저장의 정확히 한 번 처리나 종단 간 무유실을 보장하지 않습니다. 이를 위해서는 안정적인 eventId, DB 유일 제약·멱등 처리, 영속 inbox/outbox와 재처리 정책을 별도로 설계하고 검증해야 합니다.

## HMI와 수신량의 관계

HMI는 MQTT 이벤트마다 컨트롤을 갱신하지 않습니다. 서버 API 5개를 `Task.WhenAll`로 비동기 조회하고, 완료 후 1초 대기하는 기존 구조입니다. 갱신을 겹쳐 실행하지 않으므로 MQTT 수신 건수와 UI 갱신 횟수가 분리됩니다. 이번 변경은 갱신 작업 예외가 전체 조회 루프를 끝내지 않도록 보완합니다.

이 구조만으로 초당 수천 건의 PLC 처리나 UI 무정지를 입증할 수는 없습니다. 실제 Windows에서 운영 Router·DB·HMI를 연결하고 UI 입력 응답시간, API 지연, CPU·메모리, 데이터 정합성을 별도로 계측해야 합니다.

## LLM 활용과 본인 역할

원래 개발에서는 요구사항·증상·로그를 제공하고 LLM이 제안한 설계와 수정 코드를 적용·확인했습니다. 이번 장애 시험과 재연결 코드도 AI 도구를 활용해 추가했습니다. 이를 과거에 본인이 독자적으로 구현한 성과나 메모리 누수 튜닝으로 표현하지 않습니다. 프로세스와 표준입력 종료 처리 경험은 메모리 누수 계측 결과와 구분합니다.

## 실제 Windows HMI 검증 절차 (미실행)

1. 실제 Gateway·서버·DB·HMI와 Gemini를 연결합니다. 운영 메시지 형식과 유효한 작업지시/제품 데이터를 사용합니다. 본 시험의 숫자 ID 메시지는 운영 Router용 입력이 아닙니다.
2. 동일 이벤트 ID의 재전송 정책을 먼저 정한 뒤 부하를 늘립니다. 발행 수, Gateway 처리 수, DB 행 수와 상태를 대조합니다.
3. UI 스레드의 짧은 타이머로 예상 호출 시각 대비 지연을 계측하고 p95·최댓값을 기록합니다. 부하 중 버튼 조작의 응답과 중복 제어 명령 여부도 확인합니다.
4. 1분·10분·1시간으로 시간을 늘리며 API 지연, CPU, 메모리와 프로세스 수를 기록합니다. 기준값과 시험 환경을 함께 남기고 시간 경과에 따른 증가를 확인합니다.
5. 네트워크 단절·서버 중단·브로커 재시작을 각각 시험합니다. 승인 기준에 통과하기 전에는 '장시간 무유실'이나 'UI Freeze 해결'을 README 성과로 쓰지 않습니다.

초기 시험에서는 내장 브로커의 지속 세션 보관이 꺼져 있어 복구 시험이 실패했습니다. 브로커에 `WithPersistentSessions()`를 설정한 뒤 통과했습니다. Gateway 설정만으로는 오프라인 보관이 보장되지 않는다는 점을 확인한 사례입니다. 실제 Mosquitto에서는 세션/큐/영속화 설정을 별도로 확인해야 합니다.
