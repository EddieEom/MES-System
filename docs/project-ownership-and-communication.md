# 프로젝트 역할·설계 책임·기술 커뮤니케이션

이 문서는 [MES-System](../README.md) 개인 프로젝트에서 **본인이 맡은 결정**, **AI의 보조 범위**, **외부 업체 및 다른 개발자에게 설명하기 위한 자료**를 구분합니다.

## 1. 역할 구분

**요구사항 정의와 전체 시스템의 상위 구조는 프로젝트 진행자가 직접 정했습니다.** 작업자 화면에서 필요한 기능, 제어 명령과 생산 데이터의 이동 방향, 서버·통신 프로그램·DB의 역할 분리를 정리했습니다. 구현 과정에는 AI를 적극 활용했으며, 동작 확인과 검증을 거쳐 통합했습니다.

| 업무 | 본인 역할 | AI·외부 지원 |
| --- | --- | --- |
| 요구사항 정의 | START·STOP·RESET, 생산 현황, 작업지시·LOT, 검사 결과, 알람, 이력 조회 등 필요한 기능과 흐름 정의 | 누락 기능 검토 및 요구사항 구체화 보조 |
| 상위 아키텍처 | HMI ↔ Server ↔ Gateway ↔ PLC 시뮬레이터, Gemini → MQTT → Gateway → Server → DB 등 시스템 구성 방향과 책임 분리 | 모듈별 상세 설계안, 라이브러리 적용 방법 검토 보조 |
| 구현·수정 | 제안 코드를 프로젝트에 적용·연결하고 실행·오류 재현·로그 확인·수정 결과 검증 | C#·SQL·Python 코드 작성, 수정, 일부 리팩터링 및 디버깅 제안 |
| 검증 | HMI 표시, API 응답, Gateway 로그, PLC 시뮬레이터 상태, DB 저장·조회 결과 확인 | 측정 코드·테스트 시나리오·원인 후보 분석 보조 |
| 가상 설비 | 필요한 공정 및 연동 조건을 전달하고 제공된 모델을 사용하여 통합 | **㈜퍼씨엠 제공 MELSOFT Gemini 가상 설비 모델** |
| 기술 문서·소통 | 흐름·재현 조건·오류 기록·검증 범위를 정리하여 다른 사람이 추적할 수 있게 문서화 | 문서 구성·설명 표현 보조 |

이 구분은 전체 코드를 AI 없이 독자적으로 작성했다는 뜻이 아닙니다. AI는 상세 설계와 코드 작성·수정의 보조 도구였고, 프로젝트의 요구사항과 전체 구조의 방향 설정, 기능 연동, 결과 확인은 제가 수행했습니다.

## 2. 요구사항을 시스템 구조로 연결한 방법

| 요구사항 | 상위 구조에서 정한 처리 흐름 | 확인 방법 |
| --- | --- | --- |
| 작업자가 설비를 제어 | WinForms HMI → Server API → SignalR → C# Gateway → MX Component → PLC 시뮬레이터 → Gemini | 버튼 입력, Gateway 로그, PLC 상태, 가상 설비 동작 비교 |
| 설비 데이터를 수집 | Gemini → Mosquitto MQTT Broker → Gateway의 토픽 분기 → Server API | MQTT 토픽/메시지, Gateway 처리 로그와 API 응답 확인 |
| 생산 정보를 저장·조회 | Server Repository → MSSQL 저장 및 조회 → HMI API 폴링 | DB 행과 HMI 생산현황·LOT·품질 결과 비교 |
| 검사 및 LOT 상태를 일관되게 관리 | 검사 이벤트 → 품질 저장 프로시저 → 제품·LOT·작업지시 상태 갱신 | PASS/FAIL 및 LOT 전환, DB 트랜잭션 결과 확인 |
| 장애를 재현·설명 | 재현 조건 → 실행 구간별 로그 → 원인 후보 → 수정안 → 동일 조건 재실행 | 변경 전후 계측 대상과 실행 결과 구분 |

### 책임을 나눈 이유

- **HMI**는 사용자 입력과 상태 표시를 맡고, DB에 직접 연결하지 않습니다.
- **Server**는 업무 API와 DB 저장·조회, Gateway에 대한 제어 요청 전달을 맡습니다.
- **Gateway**는 MQTT 메시지 수신과 PLC 통신을 담당합니다. 실제 DB 읽기·쓰기는 서버 API를 통해 처리합니다.
- **PLC 시뮬레이터·Gemini**는 실물 생산설비가 아닌 시험 환경입니다.

## 3. 프로젝트를 다른 사람에게 설명하기 위한 문서화

모든 코드를 처음부터 읽지 않아도 현상을 재현하고 관련 담당 영역을 찾을 수 있도록, **요구사항 → 통신 경로 → 실제 파일/함수 → 입력·출력 → 검증 결과**를 연결하는 방식으로 문서를 구성했습니다.

- **구조 공유:** README의 아키텍처와 제어/수집/조회 흐름을 통해 모듈 간 책임과 연결 지점을 설명합니다.
- **코드 추적:** [코드 추적 가이드](code-trace-guide.md)에서 START 명령, MQTT 검사 결과, DB 저장, 화면 조회의 호출 지점을 따라갑니다. 개인 학습용 `MES_System_Code_Walkthrough.html`의 실행 흐름 분석도 참고해 핵심 경로를 읽기 쉬운 Markdown으로 재정리했습니다.
- **문제 보고:** [MQTT 발행 지연 트러블슈팅](../MES_Gemini_MQTT_통신최적화_트러블슈팅_2026-10-06.md)에서 정지 시점, 오류 메시지, 재현 조건, 측정 구간, 코드 변경 및 재확인 결과를 남겼습니다.
- **검증 범위 공유:** [MQTT 장애 복구·부하 시험](validation/mqtt-reliability.md)의 시험 조건과 제외 대상을 함께 기록해, 부분 시험 결과를 전체 설비 성능으로 오해하지 않도록 했습니다.

### 외부 업체와의 기술적 소통 사례

MELSOFT Gemini 연동 과정에서 통신 지연 경고와 시뮬레이션 정지 현상을 확인했습니다. 원자재 공급 중지와 시뮬레이션 중단 현상을 구분해 설명하고, Python 발행 코드와 측정 로그를 제공하여 원인 후보를 좁혔습니다. AI가 제안한 발행 프로세스 재사용 코드를 적용한 뒤 실행 결과를 다시 확인하고 전달했습니다.

이 사례에서 강조하려는 것은 **혼자 모든 문제를 해결했다는 주장**이 아니라, 다른 사람이 상황을 이해할 수 있도록 **관찰 결과·코드·측정값·적용 결과를 순서대로 전달**한 경험입니다.

### 이후 협업에 사용할 이슈 공유 형식

1. **현상/기대 결과:** 어떤 동작이 기대되었고 실제로는 무엇이 달랐는가
2. **재현 조건:** 실행 환경, 버튼/토픽, 시점, 반복 조건
3. **관련 경로:** HMI / Server / Gateway / PLC / Broker / DB 중 어디까지 확인했는가
4. **증거:** 로그, 이벤트 ID·시각, 요청·응답, DB 상태, 화면 캡처
5. **조치와 결과:** 적용한 수정안, 재시험 결과, 아직 확인하지 못한 범위

위 형식은 **기존 경험을 바탕으로 문서화한 향후 협업용 템플릿**입니다. 모든 항목을 과거에 똑같은 양식으로 전달했다고 주장하지 않습니다.

## 4. 구현·검증 범위

- 제어 명령의 서버 응답 `sent`는 **명령 전달**을 뜻하며, 설비 동작 완료 ACK가 아닙니다.
- 품질 결과 저장 프로시저 내부의 트랜잭션과 **품질 API + 이동 API 전체**의 트랜잭션은 구분합니다.
- MQTT 수신 부하 시험은 **수신 경로 시험**이며 전체 운영 Router·DB·HMI 부하 시험과 다릅니다.
- MQTT 발행 개선에서 확인한 수치는 **Python 호출 구간**으로, 종단 간 네트워크 송수신 지연이 아닙니다.
- 실물 장비 적용과 장시간 연속 가동은 이 저장소의 검증 범위가 아닙니다.

**이 문서의 목적은 기술과 소통 역량을 추상적으로 주장하는 것이 아니라, 다른 사람이 코드·실행 로그·검증 근거를 따라가며 논의할 수 있도록 정보를 정리하는 것입니다.**
